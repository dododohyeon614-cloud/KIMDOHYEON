헤딩은 누가 만드는가

차가 “지금 어느 쪽을 보고 있는가”라는 숫자 하나가 조향각 전체를 좌우한다. 그 숫자를 IMU와 GPS가 어떻게 나눠 만드는지, 코드의 실제 줄을 따라 읽는다.

○
“IMU가 방향을 주도하고, 쌓이는 오차를 GPS 진행방향으로 조금씩 보정한다”

맞다. 코드 머리말이 그대로 그렇게 적혀 있다 — 헤딩 : IMU 적분(yaw_offset) 주도 + GPS 코스로 저게인 drift/연속 미세보정. 한 번에 고치는 양은 어긋난 각도의 4 %다.

×
“초기 헤딩은 IMU가 잡는다”

반대다. 출발 직후 GPS가 초기 헤딩을 잡고, 거기에 IMU를 붙인다. IMU는 “지금 몇 도”를 알려 주지만 그건 전원을 켠 순간을 0°로 삼은 자기 기준이라 지도의 동서남북과 아무 상관이 없다.

×
“매핑한 경로의 그 지점 헤딩과 비교해서 보정한다”

아니다. 경로 파일에는 IMU 헤딩이 저장되지 않고, 보정할 때 경로를 보지도 않는다. 비교 상대는 언제나 지금 내 GPS 궤적이 실제로 그린 방향이다. 경로와의 비교는 완전히 별개의 일(CTE·lead)로 driving.py에서 한다.

△
“센서가 서로 붙는 곳은 96 : 4 헤딩 보정 하나뿐인가”

아니다. 최소 열 군데가 더 있고, 그중에는 IMU가 GPS 위치를 바꾸는 반대 방향 결합도 있다. /ego_state로 나가는 좌표는 순수한 GPS 값이 아니다 — 5장에 전부 모아 두었다.

01 / 두 센서의 성격왜 하나만으로는 안 되는가

GPS와 IMU는 서로의 약점을 정확히 덮는다. 그래서 붙인다.

　GPSIMU
말해 주는 것지도 위 절대 위치차체의 회전
주기5 Hz (0.2초에 한 번)50 Hz (0.02초에 한 번)
단기 정확도값이 툭툭 튄다매우 매끄럽다
장기 정확도몇 시간이 지나도 안 틀어진다서서히 틀어진다 (드리프트)
방향을 아는가움직여야만 안다 (궤적의 기울기)즉시 안다. 단 자기 기준
못 하는 것멈춰 있으면 방향을 모른다지도의 북쪽이 어딘지 모른다
거래 조건 GPS는 기준을 갖고 있고 IMU는 반응을 갖고 있다. 그래서 이 코드는 IMU에게 매 순간의 방향을 맡기고, GPS에게는 그 방향이 지도에서 어긋나지 않았는지 가끔 확인해 주는 역할만 맡긴다.

02 / 융합 지점붙는 자리는 딱 한 군데다 — yaw_offset

이 코드의 헤딩 공식은 파일 전체에서 단 한 줄이다.

heading = normalize_angle(raw_imu_yaw_unwrap + yaw_offset)

gps_imu.py 1023행 · main_loop() 안, 20 Hz 마다 실행

raw_imu_yaw_unwrap은 IMU가 준 각도를 그대로 이어붙인 값이고, yaw_offset은 “그 값에 몇 도를 더해야 지도 기준이 되는가”라는 보정 상수다. GPS는 heading을 절대 직접 건드리지 않는다. 오직 yaw_offset만 조금씩 민다.

0.96 : 0.04 의 정확한 뜻 새 헤딩 = 0.96 × (IMU가 말하는 방향) + 0.04 × (GPS가 말하는 방향). 5 Hz로 4 %씩 밀면 어긋난 각도의 63 %를 지우는 데 약 5초가 걸린다. “5초쯤 꾸준히 같은 말을 해야 GPS 말을 믿어 준다”는 뜻이고, 코너에서 GPS가 잠깐 엉뚱한 방향을 가리켜도 헤딩이 휘둘리지 않는 이유가 이것이다.

03 / 시작출발 직후 1미터 — 지도에 나를 붙이는 순간

전원을 켠 IMU는 “나는 0°를 보고 있다”고 말한다. 그 0°가 지도의 어디인지는 아무도 모른다. 그래서 차는 일단 조금 굴러 봐야 한다. 굴러간 자국의 방향이 곧 실제 방위이기 때문이다.

self.yaw_offset = normalize_angle(gps_heading - self.raw_imu_yaw_unwrap)
self.heading    = gps_heading

gps_imu.py 687–688행 · 헤딩 고정(lock) 성립 순간, 주행 중 딱 한 번

이 두 줄이 “지도에 붙이는” 전부다. 이후 IMU가 30° 돌면 heading도 30° 돈다 — 기준점이 정해졌으니까. 문제는 언제 이 두 줄을 실행하느냐다. 차가 비뚤게 출발하거나 GPS가 튀는 순간에 기준을 잡으면 그 오차가 주행 내내 따라다닌다. 그래서 여섯 가지 조건을 모두 만족해야 한다.

탈출구도 있다. 다른 조건은 다 맞는데 IMU 게이트만 8초 넘게 막고 있으면 경고를 남기고 그냥 통과시킨다(HEADING_LOCK_IMU_GATE_TIMEOUT_S = 8.0). 진동이 심한 노면에서 차가 영원히 출발하지 못하는 것을 막기 위한 장치다.

04 / 유지보정은 두 갈래로 들어온다

기준을 잡은 뒤에도 IMU는 시간이 갈수록 조금씩 틀어진다. 그것을 되돌리는 통로가 두 개 있는데, 성격이 완전히 다르다. 하나는 큰 어긋남을 가끔, 다른 하나는 작은 어긋남을 자주 잡는다.

회전 중에도 비교할 수 있게 만든 두 가지 보정

“GPS 궤적 방향 = 차가 향한 방향”은 직선에서만 참이다. 코너에서는 두 가지가 어긋난다. 코드는 이 둘을 각각 수식으로 되돌려 놓았고, 그래서 회전 중에도 비교가 가능해졌다.

A

안테나가 차 앞에 달려 있다 — 선회 보상

GPS 안테나는 뒷차축보다 0.865 m 앞에 있다. 코너를 돌 때 앞쪽에 달린 점은 차체 방향과 다른 쪽으로 휩쓸린다(팔 끝이 더 크게 도는 것과 같다). 그래서 “안테나가 그릴 것으로 기대되는 방향”을 먼저 계산하고, 그것과 실제 GPS 방향을 비교한다.

exp_dir = atan2( v·sinψ + ω·d·cosψ ,  v·cosψ − ω·d·sinψ )
drift   = exp_dir − gps_dir          // d = 0.865 m, ω = 요레이트

gps_imu.py 779–783행

이 보상 덕분에 회전 게이트를 12°/s → 45°/s로 풀 수 있었다. 그 전에는 곡선 위주 코스에서 보정이 103회나 건너뛰어졌다(코드 주석의 실측 기록).

B

GPS 값은 과거다 — 시간 정렬

GPS가 알려주는 위치는 “지금”이 아니라 0.23초쯤 전이다. 변위를 재는 두 점의 시간 한가운데(0.1초 전)와 수신기 내부 계산 지연(0.13초)이 겹친 값이다. 그래서 현재 헤딩이 아니라 그 시점의 헤딩을 꺼내 비교한다.

t_ref = 0.5·(t_이전 + t_지금) − 0.13
hd_ref, gz_ref = self._att_at(t_ref)   // 자세 이력에서 그때 값을 꺼냄

gps_imu.py 772–773행 · GPS_SOLUTION_LATENCY_S = 0.13

정렬 전에는 코너에서 회전 방향에 따라 ±7~10°의 가짜 drift가 번갈아 발동해 헤딩을 좌우로 흔들었다. 정렬 후 실측: drift 측정의 흩어짐 4.36° → 2.26°, 오발동 14 % → 2 %.

자기참조 금지. drift를 잴 때 쓰는 GPS 좌표는 안테나 원시 좌표다. 발행용 좌표는 heading을 써서 뒷차축으로 옮긴 값이라, 그것으로 heading을 보정하면 자기가 만든 값으로 자기를 채점하는 꼴이 된다. 코드에 그 이유가 주석으로 적혀 있다(759–760행).

헤딩 보정은 가장 유명한 결합이지 유일한 결합이 아니다. 코드를 전부 훑어 “한 센서의 값이 다른 센서의 결과를 바꾸는” 지점을 모았다. 방향에 주목할 것 — GPS→IMU만 있는 게 아니라 IMU→GPS도 있다.

여기서 자이로 값은 raw_gyro − gyro_z_bias다. 정지 중(속도 < 0.10 m/s, 회전 < 2°/s)에 자이로가 조용히 내보내는 치우침을 스스로 학습해 빼 둔 값이라, DR이 길어져도 방향이 한쪽으로 흐르는 속도가 느려진다.

07 / 도착그 숫자가 조향각이 되기까지 — 코드로 따라가기

융합 결과는 배열 하나로 driving.py에 건너간다. 헤딩은 5번째 칸이다.

state.data = [위도, 경도, x, y, heading, 속도, 0.0, 피치, 노면]
             [0]   [1]   [2] [3]  [4]     [5]   [6]  [7]  [8]

gps_imu.py 1051–1053행 → driving.py 910행 self.heading = d[4]

여기서부터 20 Hz 제어 루프 안에서 벌어지는 일을 순서대로 본다. 헤딩(ψ)이 어디에 들어가는지만 굵게 표시했다.

1

τ초 뒤의 나를 계산한다 — 지연 보상

omega_z = self.imu_gyro_z − self.gyro_bias_z    // IMU 요레이트(직접 구독)
dpsi    = omega_z * tau

adv     = self.current_speed_ms * tau
self.ctrl_lat = self.current_lat + degrees(adv * sin(psi_mid) / R)
self.ctrl_lon = self.current_lon + degrees(adv * cos(psi_mid) / (R * cos(lat)))
psi = psi + dpsi                              // 이후 계산은 전부 '예측 헤딩' 기준

핸들을 돌리라고 명령해도 차가 실제로 돌기까지 시간이 걸린다. 그래서 “지금의 나”가 아니라 “0.5초 뒤의 나”를 먼저 계산하고, 그 자세를 기준으로 모든 오차를 잰다. 위치는 반 바퀴 평균 방향(psi_mid)으로 전진시키고, 헤딩은 전체 회전량을 더한다.

2

후진 구간이면 헤딩을 뒤집는다

후진할 때 차는 뒤를 향해 간다. 진행 방향 기준으로 계산해야 좌우 판단이 맞으므로 헤딩을 180° 돌린 psi_eff를 이후 모든 식에 쓴다.

3

CTE — 경로에서 옆으로 얼마나 벗어났나

for i in range(start, end):                     // 앞뒤 웨이포인트 28개만 검사
    x0,y0 = wp[i]   − 내 위치      (미터로 변환)
    x1,y1 = wp[i+1] − 내 위치
    vx,vy = x1−x0, y1−y0                        // 선분 벡터
    t  = clamp( −(x0·vx + y0·vy) / (vx²+vy²), 0, 1)   // 수선의 발 위치
    px,py = x0 + t·vx, y0 + t·vy                // 경로 위 가장 가까운 점
    ...가장 가까운 것 선택 → best_x, best_y

cte = −best_x·sin(psi_eff) + best_y·cos(psi_eff)
if is_rev: cte = −cte

경로 위 가장 가까운 점까지의 벡터를 차량 좌표계로 회전시켜 옆방향 성분만 뽑는 식이다. 회전에 쓰는 각도가 바로 헤딩. 헤딩이 틀리면 “옆”이라는 방향의 정의 자체가 틀어진다 — 이것이 헤딩 정확도가 CTE의 핵심인 이유다.

4

lead — 지금 방향으로 계속 가면 얼마나 더 벌어질까

path_psi = atan2(seg_dy, seg_dx)                // 지금 선분이 향한 방향
he       = path_psi − psi_eff                   // 헤딩오차 θe
lead_raw = 0.876 * sin(he)                     // 휠베이스 0.73 × 1.2

cte_ctrl = clamp(cte + cte_lead, −4, 4)         // 제어에 실제로 쓰는 오차

driving.py 1522–1538행

위치는 맞는데 방향이 비뚤면 아직 안 벌어졌어도 곧 벌어진다. 그 미래분을 미리 오차에 얹는다. 시간이 아니라 거리(휠베이스)로 앞을 보기 때문에 속도가 변해도 자동으로 맞는다.

5

Pure Pursuit — 앞의 목표점을 향하는 각도

dx, dy = 목표점 − 내 위치        (미터)
lx =  dx·cos(psi_eff) + dy·sin(psi_eff)      // 차 기준 '앞쪽' 거리
ly = −dx·sin(psi_eff) + dy·cos(psi_eff)      // 차 기준 '옆쪽' 거리
alpha    = atan2(ly, lx)                        // 목표점을 바라보는 각
pp_steer = degrees( atan2(2·L·sin(alpha), LFD) )

driving.py 1782–1803행

여기서도 회전에 헤딩이 들어간다. 목표점의 지도 좌표를 차량 기준으로 옮기는 데 필요하기 때문이다. 이 결과가 조향각의 큰 줄기(약 90 %)를 만든다.

6

PID — 남은 오차를 마저 지운다

Kp, Ki, Kd = lookup_gains(v)                    // 속도별 게인표에서 보간

if cte·prev_cte < 0: cte_integral *= 0.35       // 좌우 뒤집히면 적분 감쇠
cte_integral += cte * loop_dt
cte_integral  = clamp(cte_integral, ±6.0)       // 적분 폭주 방지

p_term = Kp * cte_ctrl                          // 지연보상된 오차
i_term = Ki * cte_integral
d_term = Kd * d_term_lpf * 0.20
pid_steer = clamp(p_term + i_term + d_term, ±9.0)

raw_steer = pp_steer + pid_steer

Pure Pursuit는 “목표점을 향한다”만 알 뿐, 바람이나 좌우 무게 차이로 계속 한쪽에 치우치는 것은 못 고친다. 그 남은 몫을 PID가 맡는다. ±9°로 묶는 이유는, PID가 기하 계산(PP)을 압도하면 경로를 따라가는 게 아니라 오차만 쫓아가는 차가 되기 때문이다.

계산된 각도를 그대로 보내면 서보가 덜컥거리고 차가 흔들린다. 급변을 막고(슬루), 물리적으로 불가능한 각도를 자르고(클램프), 정지에 가까울 때는 조향을 약하게 실어(권한 램프) 출발 순간의 덜컥거림을 없앤다.

헤딩 1도가 얼마인가 코드 주석이 직접 계산해 놓았다 — IMU와 GPS 실제 방향의 오차 3~6°가 핵심 CTE 원인. CTE = sin(5°) × LFD 5 m = 0.44 m. 방향을 5° 잘못 알면 경로에서 44 cm 벗어난 채 “나는 잘 가고 있다”고 믿는다. 게다가 5장에서 본 것처럼 헤딩은 위치 좌표까지 7.5 cm 옆으로 밀어 놓는다. 융합 정밀도를 2° 이하로 끌어내리는 것이 gps_imu.py 전체의 목표였고, 그래서 게인을 0.10에서 0.04로 낮추고 시간 정렬과 선회 보상을 넣었다.

08 / 다음 단계카메라를 붙이려는 자리 — 이미 설계돼 있었다

DR 중에 GPS를 끊고 IMU + 차선 인식으로 위치·헤딩을 보정하려는 계획은 이 패키지의 이전 버전에 이미 구현되어 있었다. 현재 GitHub 버전(v6)에서는 빠졌지만, 로컬 사본에 camera_fusion.py(319행)와 lane_camera_bridge.py(213행)가 남아 있다. 설계 원칙이 파일 머리말에 그대로 적혀 있다.

· ego_state(gps_imu)는 성역 — 위치·헤딩 융합을 건드리지 않는다.
· 카메라는 driving의 "CTE 가중융합(PID 채널)"과 "속도 캡"으로만 개입한다.

게이트는 GPS 보정과 같은 철학이다 — 참조가 0.5초 이내로 신선할 것, 품질 0.4 이상, 회전 10°/s 이하(직선일 때만), 어긋남이 0.5°~15° 사이일 것, 0.5초에 한 번만. 카메라가 오검출하면 어긋남이 15°를 넘어 자동으로 무시된다.

돌아올 때 확인할 것 두 가지. ① w = 0.90은 DR에서 횡방향을 사실상 카메라에 넘긴다는 뜻이다 — 차선이 사라지는 구간(교차로, 지워진 선)의 폴백이 있는지. ② 카메라 헤딩 보정은 heading과 yaw_offset을 함께 움직인다. GPS 보정이 offset만 건드리는 것과 다른데, DR 중에는 heading이 자이로로 직접 굴러가기 때문에 둘을 같이 밀어야 DR이 끝나고 IMU + offset 경로로 복귀할 때 값이 튀지 않는다. 이 정합은 잘 잡혀 있다.
