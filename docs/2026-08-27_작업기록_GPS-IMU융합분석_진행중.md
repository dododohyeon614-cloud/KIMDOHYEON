## 1. 지금까지 확인한 것

### 1.1 융합의 실체

헤딩(차량 방향)은 다음 한 줄로 만들어진다.

```python
heading = normalize_angle(raw_imu_yaw_unwrap + yaw_offset)   # gps_imu.py 1023
```

- `raw_imu_yaw_unwrap` — IMU가 준 각도를 끊김 없이 이어붙인 값
- `yaw_offset` — "이 값에 몇 도를 더해야 지도 기준이 되는가"

GPS는 `heading`을 직접 건드리지 않는다. **오직 `yaw_offset`만 조금씩 민다.**

### 1.2 초기 헤딩은 GPS가 잡는다

애초의 가설("IMU가 초기 헤딩을 잡는다")은 코드와 반대였다.

```python
yaw_offset = normalize_angle(gps_heading - raw_imu_yaw_unwrap)   # 687
heading    = gps_heading                                          # 688
```

출발 후 아래 6개 조건을 **모두** 만족한 순간 딱 한 번 실행된다.

| 조건 | 기준값 |
|---|---|
| GPS 이동거리 | ≥ 1.0 m |
| 엔코더 누적 | ≥ 0.60 m |
| 속도 | ≥ 0.20 m/s |
| GPS 방향 흔들림(7 fix) | ≤ 15° |
| 요레이트 | ≤ 4°/s |
| IMU 총변화 | ≤ 6° |

IMU 게이트만 8초 넘게 막으면 경고 후 우회(`HEADING_LOCK_IMU_GATE_TIMEOUT_S = 8.0`).

### 1.3 보정 채널은 두 개

| | drift 보정 | 연속 미세보정 |
|---|---|---|
| 위치 | `cb_fix()` 745–825 | `_continuous_heading_correction()` 854–925 |
| 주기 | 최대 1 Hz | GPS마다 (5 Hz) |
| 대상 | \|drift\| > 6° | 0.6° ~ 8° |
| 게인 | 0.04 ~ 0.10 | 0.040 고정 |
| 회전 허용 | 45°/s (선회보상) | 10°/s |
| 시상수 | ≈ 10~25 s | ≈ 5 s |
| 비상 | > 60° & 1.5 m → 강제 리셋 | 없음 |

두 채널을 합치면 0.6°~60° 이상까지 빈틈 없이 덮인다.

### 1.4 보정 정확도를 위해 넣은 두 가지 보상

**(A) 선회 보상** — 안테나가 뒷차축보다 0.865 m 앞에 있어 코너에서 궤적이 차체 방향과 어긋난다.

```python
exp_dir = atan2(v*sin(ψ) + ω*d*cos(ψ),  v*cos(ψ) - ω*d*sin(ψ))   # 779-783
drift   = exp_dir - gps_dir
```

효과: 회전 게이트 12°/s → 45°/s 완화. (이전엔 곡선 코스에서 103회 skip 발생)

**(B) 시간 정렬** — GPS 값은 약 0.23초 과거다.

```python
t_ref = 0.5*(t_prev + t_now) - 0.13      # GPS_SOLUTION_LATENCY_S
hd_ref, gz_ref = self._att_at(t_ref)     # 그 시점의 헤딩을 이력에서 꺼냄
```

실측 효과: drift 측정 std 4.36° → 2.26°, 오발동 14% → 2%.

## 2. 새로 발견한 것 — 결합은 96:4 하나가 아니다

전수조사 결과 **최소 10곳**에서 센서가 서로를 바꾼다.

### GPS → IMU (방향의 기준 제공)
| 결합 | 위치 | 세기 |
|---|---|---|
| 초기 헤딩 lock | 687–688 | 100% · 1회 |
| drift 보정 | 809 | 4~10% |
| 연속 미세보정 | 912 | 4% |
| 강제 리셋 | 797–799 | 100% |

### IMU → GPS (반대 방향 — 잘 알려지지 않음)
| 결합 | 위치 | 내용 |
|---|---|---|
| **안테나 → 뒷차축 투영** | 613–614 | IMU 헤딩 방향으로 GPS 좌표를 0.865 m 뒤로 옮김 |
| GPS 속도 부호 판정 | 517–518 | 궤적 방향과 헤딩을 비교해 전진/후진 결정 |

```python
rear_x = curr_x - 0.865 * cos(ψ)     # 613
rear_y = curr_y - 0.865 * sin(ψ)     # 614
```

→ **`/ego_state`로 나가는 위치는 순수한 GPS 값이 아니다.**
헤딩이 5° 틀리면 위치도 0.865 × sin 5° ≈ 7.5 cm 옆으로 밀린다.

### 엔코더가 끼어드는 자리
| 결합 | 위치 |
|---|---|
| 자이로 바이어스 학습 게이트(정지 판정) | 459–464 |
| DR 위치 적분(엔코더 거리 × IMU 방향) | 420–431 |
| 선회보상 기대방향(v, ω 동시 사용) | 779–783 |
| drift 보정 게이트(GPS 0.35 m AND 엔코더 0.5 m/s) | 768 |

### driving.py의 두 번째 융합층
`driving.py`는 `/imu/data`를 **직접 한 번 더 구독한다** (777행).

| 결합 | 위치 | 내용 |
|---|---|---|
| 미래 자세 예측 | 1361 | IMU 요레이트로 τ=0.50 s 뒤 헤딩 계산 |
| IMU 없을 때 폴백 | 1365–1367 | `ω = v·tan(δ)/L` — 조향 명령에서 요레이트를 지어냄 |
| 속도 계획 보수화 | 1593 | IMU 끊기면 ω_n 상한 0.95 → 0.80 |
| DR 감속 | 933, 1670 | 상태 문구의 "[DR중]"을 읽고 목표속도 ×0.6 |
| 속도 출처 교체 | 917–920 | 엔코더 0.5 s 끊기면 ego 속도로 대체 |

**결론** — 결합 방식은 네 종류다: 기준 제공 / 좌표 변환 / 게이트 / 폴백.
96:4는 그중 첫 번째의 대표 사례일 뿐이다.

## 3. 헤딩 → 조향각 경로

`/ego_state[4]` → `driving.py:910` → 20 Hz 제어 루프에서 다음 순서로 사용된다.

1. **지연 보상** (1356–1374) — `ψ_예측 = ψ + ω·τ`, τ = 0.50 s
2. **후진 처리** (1380–1382) — `psi_eff = ψ + π` (후진 구간)
3. **CTE** (1192–1210) — `cte = −best_x·sin(psi_eff) + best_y·cos(psi_eff)`
4. **lead** (1522–1538) — `θe = path_psi − psi_eff`, `lead = 0.876·sin(θe)`
5. **Pure Pursuit** (1782–1803) — `α = atan2(ly, lx)`, `δ_pp = atan2(2L·sinα, LFD)`
6. **PID** (1809–1840) — `raw_steer = pp_steer + pid_steer`, PID는 ±9°로 제한
7. **다듬기** (1869–1897) — 지수평활 0.5 → 슬루 1.3°(직선)/2.5~3.2°(코너) → ±20° 클램프 → 저속 권한 램프

헤딩은 1·2·3·4·5 다섯 곳 모두에 들어간다.
코드 주석의 실측: **IMU와 GPS 방향 오차 3~6°가 핵심 CTE 원인. CTE = sin(5°) × LFD 5 m = 0.44 m.**

## 4. 다음 단계 — 카메라 융합

계획: DR(GPS 두절/불신) 시 GPS를 끊고 **IMU + 차선 인식**으로 위치·헤딩 보정.

**이 설계는 이전 버전에 이미 구현되어 있었다.** 현재 GitHub v6에서는 제거되었으나,
로컬 사본에 `camera_fusion.py`(319행), `lane_camera_bridge.py`(213행)가 남아 있다.

설계 원칙(파일 머리말 원문):
```
· ego_state(gps_imu)는 성역 — 위치·헤딩 융합을 건드리지 않는다.
· 카메라는 driving의 "CTE 가중융합(PID 채널)"과 "속도 캡"으로만 개입한다.
· Pure Pursuit(조향의 94%)는 계속 GPS 경로를 조준한다. 카메라는 발밑 이탈량만.
· cam_enable=False(기본) = 섀도 모드: 융합·캡을 전혀 적용하지 않고 로깅만
```

두 개입 경로:

| 경로 | 내용 | 평상시 | DR 중 |
|---|---|---|---|
| CTE 가중융합 | `cte = w·카메라CTE + (1−w)·GPS CTE` | w = 0.40 | w = 0.90 |
| DR 헤딩 보정 | 차선+지도접선 절대헤딩으로 자이로 drift 상쇄 | 미사용 | 게인 0.08 |

```python
drift = normalize_angle(heading - cam_head_ref)
corr  = drift * 0.08
heading    -= corr
yaw_offset -= corr        # 둘을 같은 양만큼 → DR 종료 시 정합 유지
```

게이트: 참조 0.5 s 이내 신선 / 품질 ≥ 0.4 / 회전 ≤ 10°/s / 어긋남 0.5°~15° / 0.5 s 간격.

### 복원 시 확인할 것
1. `w = 0.90`은 DR에서 횡방향을 사실상 카메라에 넘긴다 — 차선이 사라지는 구간(교차로, 지워진 선)의 폴백 필요.
2. 카메라 헤딩 보정은 `heading`과 `yaw_offset`을 **함께** 움직인다(GPS 보정은 offset만).
   DR 중 heading이 자이로로 직접 굴러가기 때문이며, 이 정합 자체는 올바르게 잡혀 있다.
