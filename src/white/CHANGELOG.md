## 2026-08-14 14:52 — GPS 품질 5등급 판별 ★status 뒤에 숨어 있던 RTK Float★

### 무엇이 문제였나

`gps_imu.py` 는 GPS 를 믿을지 말지를 **`msg.status.status` 하나로만** 판단했다
(`cb_fix`). 이름이 `is_rtk_fixed` 인데 실제 조건은 `status >= FIX`(0 이상)이라
저정밀 fix 까지 전부 True 가 되고, 그대로 `fused_x/y` 에 반영된다.

그런데 **`status` 는 정확도를 적는 칸이 아니다.** `sensor_msgs/NavSatStatus` 의
상수는 넷뿐이고, 그 분류축은 ★보정을 어디서 받았는가★ 다.

```
-1 NO_FIX     측위 불가
 0 FIX        아무한테도 안 받음
 1 SBAS_FIX   위성한테 받음      (SBAS = 위성기반 보정)
 2 GBAS_FIX   땅에서 받음        (GBAS = 지상 기준국 보정 = RTK)
```

RTK 는 반송파 정수 모호도를 풀었든(**Fixed**, 오차 1~2cm) 못 풀었든(**Float**,
오차 30cm~2m) **지상 기준국 보정을 받는 건 똑같아서 둘 다 `status=2`** 로 들어온다.
메시지 정의에 그 둘을 구분할 자리가 아예 없다. 드라이버가 정보를 뭉갠 게 아니라,
정확도는 애초에 `position_covariance` 쪽에 담도록 설계돼 있고 드라이버는 그대로
담아 보내고 있었다 — ★우리 코드가 그 칸을 한 번도 안 읽었을 뿐이다★
(`position_covariance` 는 이번 수정 전까지 white_ws 전체에서 등장하지 않는다).

### 실측 근거 — 로스백 49개 / fix 14,394 샘플

`status=2` 인 14,166 개의 수평 std 가 **두 덩어리로 완전히 갈라진다.**

| 수평 std | 개수 | 비중 | 정체 |
|---|---|---|---|
| 0.0106 ~ 0.018 m | 13,540 | 95.6% | GGA quality 4 = **RTK Fixed** |
| *(0.018 ~ 1.778 m)* | **0** | — | ★표본이 단 하나도 없다 — 약 100배 공백★ |
| 1.778 ~ 3.04 m | **626** | **4.4%** | GGA quality 5 = **RTK Float** |

status 별 교차표(전체 14,394):

| status | 수평 std | 개수 | 정체 |
|---|---|---|---|
| 2 | 작음 | 13,540 | RTK Fixed |
| **2** | **큼** | **626** | **RTK Float** ← 지금까지 '오차 2cm' 로 믿어 온 것 |
| 1 | 0.032~0.1 m | 60 | SBAS/DGPS |
| 0 | 큼 | 168 | 단독측위 |

덩어리 간 비율이 드라이버의 등급별 EPE 기본값 비율과 일치한다 —
관측 **4.9배 / 188배** ↔ EPE **0.1÷0.02=5배 / 4.0÷0.02=200배**.
`position_covariance_type` 은 전부 1(APPROXIMATED, HDOP 근사)이었다.

**열화 구간은 11회·총 168.6초, 최장 61.8초 / 47.8초 연속.**

### ⚠️ 부수 발견 — GPS 는 '튀지' 않는다

작업 초기 가정("신호가 나쁘면 위치가 순간적으로 튄다")은 **데이터와 달랐다.**
fix 간 이동량(0.2초 정규화)을 등급별로 비교하면 사실상 같다.

| 등급 | p50 | p99 | 최대 |
|---|---|---|---|
| RTK Fixed | 0.383 m | 0.647 m | 0.734 m |
| SBAS | 0.481 m | 0.641 m | 0.654 m |
| Float·단독 | 0.363 m | **0.649 m** | 0.736 m |

등급 전환 순간에도 점프가 없다 — Fixed→열화 최대 0.54m, **열화→Fixed 복귀 최대
0.625m**. 즉 열화 fix 는 순간이동하지 않고 **매끄럽게 어긋난다**(bias 성질).

이 두 가지가 따라온다:

1. **한 스텝짜리 이상치 게이트(원뿔/innovation)로는 이 문제를 못 잡는다.**
   매끄러운 변화는 그런 검사를 그냥 통과한다. 등급을 직접 읽는 수밖에 없다.
2. **"Float 이면 무시하고 DR 로 버틴다" 도 답이 아니다.** 최장 61.8초를 자이로만으로
   버티면 횡오차가 약 3m 까지 쌓인다(잔차 bias 0.05°/s, 1.8 m/s 가정:
   `v·b·T²/2 ≈ 2.8m`) — Float 보다 나쁘다. **버리는 게 아니라 덜 믿는** 쪽이 맞다.

### 무엇을 바꿨나

**`gps_imu.py`**

- 파일 상단에 `GQ_*` 5등급 상수 + 라벨/이모지 신설. ★`GPS_STATUS_*`(드라이버 원본
  해석용)와 이름을 완전히 분리했다★ — 같은 이름에 값만 바꾸면 기존
  `>= GPS_STATUS_FIX` 비교 3곳이 **에러 없이 조용히 항상 참**이 되어
  `is_rtk_fixed` 가 NO FIX 에서도 True 가 되고 DR 폴백이 영영 안 걸린다.
- `_classify_gps_quality()` 추가 — `status` 와 `position_covariance` 를 같이 읽는다.
  `status=2` 일 때만 covariance 로 가르고, 0/1 은 이미 1:1 대응이라 볼 필요가 없다.
- `/gps_quality` (Int32) 발행 신설. `/gps_status` 문자열은 사람이 보는 용도라
  파싱이 불편해서, **로스백에 숫자로 남기려고** 토픽을 따로 뒀다.
- 등급 전환 시 경고 로그(수평 std 동봉).
- `/gps_status` 라벨을 5단계로. ★`[DR중]`·`[GPS복구중]` 태그는 그대로 유지★ —
  `driving.py`(`cb_gps_status`)는 이 문자열을 부분문자열로만 검사하므로 무영향.

```
GQ_FIXED (4)  status=2 & std <  0.15m   RTK Fixed  ~2cm      실측 94.1%
GQ_FLOAT (3)  status=2 & std >= 0.15m   RTK Float  ~0.3-2m   실측  4.3%  ★신규★
GQ_SBAS  (2)  status=1                  SBAS/DGPS  ~1m       실측  0.4%
GQ_GPS   (1)  status=0                  단독측위   ~2-5m     실측  1.2%
GQ_NONE  (0)  status=-1 또는 좌표 비정상
```

임계값 `GQ_FIXED_STD_MAX = 0.15m` — 실측 경계(Fixed 최대 0.018m / Float 최소
1.778m) 양쪽으로 **8~12배 여유**다. 오판이 나려면 HDOP 가 7.5 이상 나빠지거나
0.038 이하로 좋아져야 하는데 둘 다 현실에서 일어나지 않는다.
`covariance_type=UNKNOWN` 이면 **보수적으로 Float** 로 본다 — Fixed 로 오판하면
2m 짜리를 2cm 로 믿게 되어 훨씬 위험하다.

**`sensor_monitor.py`**

- 5단계 등급 + 수평 std 표시, 드라이버 원본 status 는 참고용으로 병기.
- 경고 기준을 `status < 2` → **`등급 < 4`** 로 교체. 기존 기준은 RTK Float 를
  정상으로 통과시켜 경고가 뜨지 않았다.

### 다음에 무엇을 확인해야 하나

1. **`/gps_quality` 로 Float 빈도·지속시간을 실주행에서 집계한다.** 이 데이터가
   있어야 다음 단계(칼만필터 측정잡음 `R`)를 근거 있게 정할 수 있다.
2. **Float 의 실제 오차를 재야 한다.** 드라이버가 붙이는 std 2.5m 는 등급별
   보수적 상수(EPE 4.0 × HDOP)지 실측값이 아니다. 이번 로그에서 복귀 점프가
   0.625m 이하였다는 건 실제 오차가 그보다 훨씬 작았다는 뜻이다.
   ★이 값을 그대로 `R` 에 넣으면 필터가 멀쩡한 GPS 를 최장 61.8초간 무시한다★
3. **실차(gold_ws/white806)는 같은 분석을 다시 해야 한다.** 수신기·안테나·주행환경이
   달라 Float 비중과 지속시간이 다를 수 있다. 상수를 그대로 옮기면 안 된다.
4. (선택) 더 정확한 등급이 필요하면 런치를 `nmea_topic_serial_reader` +
   `nmea_topic_driver` 조합으로 바꿔 `/nmea_sentence` 를 받고 **GGA 6번째 필드를
   직접** 읽는 방법이 있다. EPE 기본값에 의존하지 않는다.
   (설치된 패키지에 해당 실행파일이 있는지 실차에서 확인 필요)
